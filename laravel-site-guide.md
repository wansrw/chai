## 1. Как устроено приложение Laravel

Типичный запрос проходит по цепочке:

```text
Браузер
  → маршрут (routes/web.php)
  → middleware (например, auth)
  → контроллер (app/Http/Controllers)
  → модель и база данных (app/Models, migrations)
  → Blade-шаблон (resources/views)
  → HTML-ответ браузеру
```

Для примера магазина:

```text
GET /catalog
  → CatalogController
  → получить товары из catalog
  → resources/views/catalog.blade.php

POST /cart/items/15
  → CartController
  → сохранить ID товара и количество в сессии
  → показать корзину

POST /orders
  → auth middleware
  → проверить данные формы
  → создать заказ и строки заказа в транзакции
  → очистить корзину
  → перейти в личный кабинет
```

**Правило разделения ответственности:**

- **Маршрут** отвечает на вопрос: какой URL и HTTP-метод вызывает действие?
- **Контроллер** принимает запрос, проверяет входные данные и координирует действие.
- **Модель** описывает сущность и связи с таблицами.
- **Миграция** описывает структуру таблиц в коде.
- **Blade** отображает данные и формы, но не должен решать бизнес-правила.

## 2. Начало каждого проекта — требования и план

До создания файлов зафиксируй, что именно должен делать сайт. Это экономит время и не даёт начать с красивой страницы, забыв про бизнес-процесс.

### 2.1 Краткое описание

Заполни для каждого сайта:

| Вопрос | Ответ |
|---|---|
| Для кого сайт? | Например: покупатели чая |
| Что пользователь должен сделать? | Найти товар и оформить заказ |
| Главные страницы | Главная, каталог, карточка товара, корзина, профиль |
| Какие роли есть? | Гость, пользователь, администратор |
| Какие данные храним? | Товары, пользователи, заказы, позиции заказов |
| Что происходит после действия? | Заказ сохраняется, пользователь видит подтверждение |
| Нужны ли оплата и доставка? | Отдельно решить до разработки |

### 2.2 Таблица страниц и доступа

| Страница / действие | Гость | Вошедший пользователь | Администратор |
|---|---:|---:|---:|
| Главная | Да | Да | Да |
| Каталог | Да | Да | Да |
| Корзина | Да | Да | Да |
| Оформление заказа | Нет или по правилам проекта | Да | Да |
| Мои заказы | Нет | Только свои заказы | По отдельному админ-разделу |

Не полагайся на скрытие кнопки в интерфейсе. Доступ всегда проверяй на сервере через middleware, policy или другой механизм авторизации.

### 2.3 Список сущностей

Для каждой сущности выпиши поля, обязательность и связи:

```text
Product
- name: строка, обязательно
- description: текст, необязательно
- price: decimal, обязательно
- image_path: строка, необязательно
- category_id: внешний ключ

Order
- user_id: кто оформил
- customer_name
- phone
- address
- status
- total

OrderItem
- order_id
- product_id (или исходный ID товара)
- product_name (снимок на момент заказа)
- unit_price (снимок цены)
- quantity
```

### 2.4 Сначала сценарии, потом код

Пример пользовательского сценария:

1. Гость открывает каталог.
2. Добавляет товар в корзину.
3. Изменяет количество или удаляет позицию.
4. Нажимает «Оформить заказ».
5. Если не вошёл — проходит авторизацию и возвращается к оформлению.
6. Вводит телефон и подтверждает заказ.
7. Сервер повторно получает актуальные товары и цены из БД.
8. Сервер атомарно сохраняет заказ и позиции.
9. Корзина очищается.
10. Пользователь видит заказ в личном кабинете.

Для каждой функции задай критерии готовности. Например: «нельзя оформить заказ с пустой корзиной», «цена берётся из базы, а не из формы».

## 3. Создание проекта на Windows и XAMPP

### 3.1 Выбери совместимые версии

Перед установкой сверь:

- версию PHP, которую поддерживает выбранная версия Laravel;
- версии расширений PHP;
- версию MySQL/MariaDB на сервере;
- версию Node.js, если собираются frontend-ресурсы;
- возможности целевого хостинга.

В этом сайте в `composer.json` указаны Laravel `^8.75` и PHP `^7.3|^8.0`. Это описание именно этого проекта, а не шаблон для нового сайта.

### 3.2 Создание проекта

Пример для PowerShell, если Composer уже установлен:

```powershell
Set-Location W:\xampp\htdocs
composer create-project laravel/laravel my-site
Set-Location W:\xampp\htdocs\my-site
```

Если нужен конкретный major Laravel, укажи совместимое ограничение версии в команде создания и проверь актуальную инструкцию Laravel. Не обновляй major-версию случайно в уже работающем проекте.

### 3.3 Установка зависимостей существующего проекта

```powershell
Set-Location W:\xampp\htdocs\my-site
composer install
npm install
```

`composer install` использует версии из `composer.lock`; `composer update` пересчитывает версии зависимостей и может внести несовместимые обновления. Для обычного восстановления проекта используй `install`.

### 3.4 Запуск локально

В одном терминале можно запустить Laravel dev server:

```powershell
Set-Location W:\xampp\htdocs\my-site
& W:\xampp\php\php.exe artisan serve
```

Обычно сайт будет доступен по адресу, который напечатает команда, например `http://127.0.0.1:8000`.

Можно также настроить Apache VirtualHost. Корневой каталог сайта должен указывать на папку `public`, а не на корень Laravel-проекта. Не публикуй наружу `.env`, `vendor`, `storage` и исходники приложения.

### 3.5 Команда PHP для XAMPP

Если команда `php` не найдена в PATH, вызывай PHP XAMPP напрямую:

```powershell
& W:\xampp\php\php.exe artisan route:list
```

Перед Artisan-командой перейди в корень проекта: там должен лежать файл `artisan`.

## 4. Настройка окружения и базы данных

### 4.1 Файл `.env`

1. Создай `.env` на основе `.env.example`, если его ещё нет.
2. Настрой имя приложения, адрес и параметры БД.
3. Сгенерируй ключ приложения.

```powershell
Copy-Item .env.example .env
& W:\xampp\php\php.exe artisan key:generate
```

Пример настроек, **без настоящего пароля**:

```dotenv
APP_NAME="My Site"
APP_ENV=local
APP_DEBUG=true
APP_URL=http://127.0.0.1:8000

DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=my_site
DB_USERNAME=root
DB_PASSWORD=
```

Не копируй пример вслепую: имя пользователя и пароль зависят от установки MySQL.

> [!danger] Секреты
> Не отправляй `.env` в Git, скриншоты, чаты и публичные сервисы. В репозитории должен быть `.env.example` с пустыми или демонстрационными значениями, но без секретов.

### 4.2 Создание БД

1. Запусти MySQL в XAMPP.
2. Создай пустую базу в phpMyAdmin или консоли.
3. Выбери `utf8mb4` и подходящую collation.
4. Проверь доступ приложения через миграции.

Не подключай локальную разработку к production-базе. Для разработки, тестов и production желательно использовать отдельные базы и учётные записи с минимальными правами.

### 4.3 Конфигурационный кэш

После изменения `.env` в окружении с закэшированной конфигурацией Laravel может продолжать видеть старые значения:

```powershell
& W:\xampp\php\php.exe artisan config:clear
```

Не вызывай `config:cache` во время обычной локальной разработки без необходимости.

## 5. Структура проекта — куда класть код

| Путь | Назначение |
|---|---|
| `routes/web.php` | Страницы и действия браузерного сайта |
| `routes/api.php` | API-маршруты, если проект их использует |
| `app/Http/Controllers/` | Контроллеры запросов |
| `app/Http/Requests/` | Повторно используемая серверная валидация |
| `app/Models/` | Eloquent-модели и связи |
| `app/Policies/` | Проверка доступа к конкретным сущностям |
| `database/migrations/` | Изменения структуры БД |
| `database/seeders/` | Начальные/демонстрационные данные |
| `database/factories/` | Генерация тестовых сущностей |
| `resources/views/` | Blade-шаблоны |
| `resources/views/layouts/` | Общие макеты страниц |
| `resources/css/`, `resources/js/` | Frontend-исходники Laravel Mix/Vite |
| `public/` | Публичные файлы и точка входа веб-сервера |
| `storage/` | Логи, временные и загруженные файлы |
| `tests/Feature/` | Проверки маршрутов и пользовательских сценариев |
| `tests/Unit/` | Изолированные проверки логики |

В чайном магазине используются `Catalog`, `Categorys`, `Order`, `OrderItem`, а также Blade-файлы `catalog.blade.php`, `cart.blade.php`, `checkout.blade.php`, `home.blade.php`. Устаревшие или необычные имена таблиц и моделей не копируй в новый проект без причины: например, для новой модели категории лучше выбрать согласованное имя `Category`.

## 6. Проектирование таблиц и миграций

### 6.1 Миграция — источник правды о схеме

Новая схема должна создаваться миграциями, а не только ручной настройкой phpMyAdmin. Так проект можно развернуть повторно на компьютере другого разработчика и в тестовой среде.

Создать модель с миграцией:

```powershell
& W:\xampp\php\php.exe artisan make:model Product -m
```

Или отдельную миграцию:

```powershell
& W:\xampp\php\php.exe artisan make:migration create_products_table --create=products
```

### 6.2 Пример таблицы товаров

```php
Schema::create('products', function (Blueprint $table) {
    $table->id();
    $table->foreignId('category_id')->nullable()->constrained()->nullOnDelete();
    $table->string('name');
    $table->text('description')->nullable();
    $table->decimal('price', 10, 2);
    $table->string('image_path')->nullable();
    $table->boolean('is_active')->default(true);
    $table->timestamps();
});
```

Проверь, что используемые сокращения методов доступны именно в установленной версии Laravel и поддерживаются текущей БД.

### 6.3 Пример таблиц заказов

В магазине заказ и товарная позиция разделены:

```text
orders
- id
- user_id
- customer_name
- phone
- address
- comment
- total
- status
- timestamps

order_items
- id
- order_id
- product_id
- product_name
- unit_price
- quantity
- timestamps
```

Почему в `order_items` хранятся `product_name` и `unit_price`: заказ должен показывать, что именно и по какой цене клиент заказал, даже если позже изменятся название или цена товара.

### 6.4 Важные правила схемы

- Деньги храни как `DECIMAL`, не как `FLOAT`.
- Количество — целое число с разумным ограничением.
- Добавляй внешние ключи для сущностей с гарантированными отношениями.
- Продумай поведение при удалении: `cascade`, `restrict` или `nullOnDelete`.
- Удаление товара не должно случайно удалять историю заказа.
- Добавляй индексы на часто используемые фильтры: `user_id`, `status`, даты и внешние ключи.
- Ограничивай длину строк и делай поля nullable только по реальному бизнес-правилу.
- Проверяй, что миграция `order_items` выполняется после миграции `orders`.
- Новая миграция должна добавлять/менять нужную структуру и иметь понятный `down()`.

### 6.5 Запуск миграций

```powershell
& W:\xampp\php\php.exe artisan migrate:status
& W:\xampp\php\php.exe artisan migrate
```

`migrate` обычно только добавляет таблицы и изменения, описанные в новых миграциях. Перед любыми командами, способными удалить таблицы или данные, прочитай их точный эффект и проверь, какую БД выбрало приложение.

> [!danger] Не запускай на существующих данных без проверки
> `migrate:fresh` удаляет все таблицы выбранной базы. `migrate:refresh` откатывает миграции и запускает их заново. Для production это может означать потерю данных.

### 6.6 Если база уже создана вручную

В текущем сайте основная схема `users`, `catalog`, `categorys` была создана вне набора миграций. Это делает свежую установку и `RefreshDatabase` тесты неполными.

В будущих проектах:

1. Сразу добавляй миграции базовых таблиц.
2. Не рассчитывай, что таблица есть только потому, что она существует в твоём XAMPP.
3. Если подключаешь уже работающую БД, сначала сравни схему, сделай резервную копию и составь безопасные миграции для её текущего состояния.
4. Не добавляй миграцию, повторно создающую уже существующую таблицу, не проверив план выкладки.

## 7. Модели и связи Eloquent

Модель связывает приложение с таблицей:

```php
namespace App\Models;

use Illuminate\Database\Eloquent\Model;

class Product extends Model
{
    protected $fillable = [
        'category_id',
        'name',
        'description',
        'price',
        'image_path',
        'is_active',
    ];

    public function category()
    {
        return $this->belongsTo(Category::class);
    }
}
```

Примеры связей:

```php
// Category.php
public function products()
{
    return $this->hasMany(Product::class);
}

// User.php
public function orders()
{
    return $this->hasMany(Order::class);
}

// Order.php
public function user()
{
    return $this->belongsTo(User::class);
}

public function items()
{
    return $this->hasMany(OrderItem::class);
}
```

### Массовое заполнение

`$fillable` разрешает массовое присвоение перечисленных полей. Не добавляй туда бездумно `is_admin`, `user_id`, `total`, `status` и другие чувствительные поля. Для заказа сервер сам устанавливает пользователя, цену, итог и начальный статус.

### Если имена таблиц нестандартные

Laravel ожидает таблицу во множественном числе от имени модели. Если таблица уже называется иначе, явно объяви её:

```php
protected $table = 'catalog';
```

Не переименовывай таблицу «для красоты», если проект уже использует её в рабочей БД: сначала подготовь миграцию и учти существующие данные.

## 8. Маршруты и контроллеры

### 8.1 Маршруты

Используй имена маршрутов, чтобы не зашивать адреса в шаблоны:

```php
use App\Http\Controllers\CatalogController;
use App\Http\Controllers\CartController;
use App\Http\Controllers\OrderController;
use Illuminate\Support\Facades\Route;

Route::get('/catalog', [CatalogController::class, 'index'])
    ->name('catalog.index');

Route::get('/cart', [CartController::class, 'index'])
    ->name('cart.index');

Route::post('/cart/items/{product}', [CartController::class, 'store'])
    ->name('cart.items.store');

Route::get('/checkout', [CartController::class, 'checkout'])
    ->middleware('auth')
    ->name('checkout');

Route::post('/orders', [OrderController::class, 'store'])
    ->middleware('auth')
    ->name('orders.store');
```

Это современный для данного синтаксиса Laravel стиль; в текущем сайте некоторые маршруты записаны полностью квалифицированными именами. Следуй стилю проекта, который создаёшь, и проверяй фактические версии.

### 8.2 Выбирай HTTP-метод по назначению

| Метод | Применение |
|---|---|
| `GET` | Показ страницы/данных, не изменяет состояние |
| `POST` | Создание, действие или отправка формы |
| `PATCH` | Частичное изменение сущности |
| `PUT` | Полная замена ресурса |
| `DELETE` | Удаление |

Не выполняй удаление или создание заказа через `GET`-ссылку.

### 8.3 Controller с проверкой данных

```php
public function index(Request $request)
{
    $filters = $request->validate([
        'category' => ['nullable', 'integer', 'exists:categories,id'],
        'price_from' => ['nullable', 'numeric', 'min:0'],
        'price_to' => ['nullable', 'numeric', 'min:0'],
    ]);

    $products = Product::query()
        ->where('is_active', true)
        ->when($filters['category'] ?? null, function ($query, $id) {
            $query->where('category_id', $id);
        })
        ->when($filters['price_from'] ?? null, function ($query, $price) {
            $query->where('price', '>=', $price);
        })
        ->paginate(12)
        ->appends($request->query());

    return view('catalog.index', compact('products'));
}
```

Для большого набора правил вынеси проверку в `FormRequest`. Не пиши всю бизнес-логику в `routes/web.php` или Blade.

### 8.4 Не возвращай успех при ошибке

Если введённое значение недопустимо:

- верни Laravel validation errors;
- покажи ошибку пользователю;
- не создавай частичную сущность;
- не подменяй ошибку фиктивным успешным результатом.

Для нескольких записей, которые должны создаться вместе, используй `DB::transaction()`.

## 9. Blade, формы и интерфейс

### 9.1 Общий layout

Создай общий layout, например `resources/views/layouts/app.blade.php`, и наследуй его:

```blade
@extends('layouts.app')

@section('content')
    <main class="container py-4">
        <h1>{{ $title }}</h1>
    </main>
@endsection
```

Общий layout обычно содержит:

- `<!doctype html>`, язык и `meta viewport`;
- заголовок и стили;
- navbar;
- `@yield('content')`;
- footer;
- JavaScript.

Меню и подвал меняй в одном месте, а не копируй на каждую страницу.

### 9.2 Формы

Для каждой формы, меняющей данные:

```blade
<form method="POST" action="{{ route('cart.items.store', $product) }}">
    @csrf
    <input name="quantity" type="number" min="1" max="99"
           value="{{ old('quantity', 1) }}">

    @error('quantity')
        <div class="text-danger">{{ $message }}</div>
    @enderror

    <button type="submit">Добавить</button>
</form>
```

Для `PATCH`, `PUT`, `DELETE` HTML-форма всё равно отправляет `POST`, поэтому добавь директиву:

```blade
@csrf
@method('PATCH')
```

### 9.3 Вывод данных и ошибки

- `{{ $value }}` экранирует вывод и подходит для обычного текста.
- Не выводи пользовательский HTML через `{!! !!}`, если он не очищен безопасным способом.
- Для ошибок используй `@error('field')`.
- Для старого значения формы используй `old('field')`.
- Для flash-сообщений используй `session('status')` или согласованный формат.
- Форматируй деньги одинаково во всех компонентах.

### 9.4 Bootstrap и адаптивность

В чайном магазине внешний вид использует Bootstrap 5 и тёмную палитру. Для нового проекта:

1. Выбери дизайн-систему и способ подключения — CDN или сборка.
2. Создай карточки, формы, кнопки и цвета как повторяемые паттерны.
3. Проверяй экран телефона и широкого экрана.
4. Используй семантические элементы: кнопки для действий, ссылки для навигации.
5. У кнопки-иконки добавляй текстовую метку или `aria-label`.
6. Не вкладывай `<button>` внутрь `<a>` — это некорректная структура.
7. Не привязывай всю стилизацию к длинным inline-style; при росте интерфейса вынеси её в CSS.

## 10. Авторизация и личный кабинет

### 10.1 Не смешивай авторизацию и права доступа

- **Authentication** отвечает: кто вошёл?
- **Authorization** отвечает: может ли именно этот пользователь выполнить действие с этой записью?

`auth` middleware защищает страницу от гостей:

```php
Route::get('/account', [AccountController::class, 'index'])
    ->middleware('auth')
    ->name('account');
```

Но для заказов фильтруй записи по текущему пользователю:

```php
$orders = $request->user()
    ->orders()
    ->with('items')
    ->latest()
    ->get();
```

Не загружай любой заказ по ID, а потом не показывай его без проверки владельца. Безопасный вариант:

```php
$order = $request->user()->orders()->with('items')->findOrFail($id);
```

### 10.2 Регистрация и вход

Текущий сайт использует `laravel/ui` и `Auth::routes()` (см. `routes/web.php`). В новых версиях Laravel способ установки стартовой авторизации может отличаться. Перед установкой проверь документацию и совместимость выбранного starter kit с версией проекта.

### 10.3 Страница пользователя

В личном кабинете обычно показывают:

- имя и контактные данные;
- заказы пользователя;
- статус, дату и состав заказа;
- ссылки на детали заказа;
- действия профиля — только если они действительно реализованы.

Не показывай пользователю чужие заказы, даже если он вручную подставил другой ID в URL.

## 11. Пример потока магазина — каталог, корзина и заказ

Этот раздел — переносимый образец архитектуры из чайного магазина.

### 11.1 Каталог

1. `GET /catalog` вызывает контроллер каталога.
2. Контроллер получает активные товары через Eloquent.
3. Фильтры проходят validation.
4. Список ограничен пагинацией.
5. Blade выводит карточки и форму «В корзину».

### 11.2 Корзина

Для корзины без авторизации можно хранить в сессии только идентификатор товара и количество:

```php
[
    12 => 2,
    18 => 1,
]
```

Плюсы: корзина доступна гостю, не нужна таблица до оформления заказа. Минусы: она привязана к сессии и не обязательно переносится между устройствами.

При отображении страницы сервер должен:

1. Прочитать ID и количества из сессии.
2. Получить актуальные товары из базы.
3. Игнорировать или удалить товары, которых больше нет.
4. Рассчитать суммы на сервере.
5. Ограничить количество допустимым диапазоном.

Не принимай цену из скрытого поля формы: скрытое поле всё равно контролирует браузер пользователя.

### 11.3 Оформление

Для заказа по звонку форма обычно принимает имя и телефон. Адрес и комментарий — по правилам проекта. Сервер затем:

1. Повторно валидирует контактные данные.
2. Получает товары по ID из БД.
3. Берёт цены из БД.
4. Проверяет, что корзина не пуста и позиции существуют.
5. Рассчитывает итог.
6. Создаёт заказ и строки в транзакции.
7. Сохраняет снимок названия и цены в строках заказа.
8. Очищает сессию только после успешной транзакции.
9. Показывает подтверждение и заказ в личном кабинете.

Схематичный пример:

```php
$order = DB::transaction(function () use ($request, $items, $total) {
    $order = Order::create([
        'user_id' => $request->user()->id,
        'customer_name' => $request->input('customer_name'),
        'phone' => $request->input('phone'),
        'total' => $total,
        'status' => 'new',
    ]);

    $order->items()->createMany($items);

    return $order;
});

$request->session()->forget('cart');
```

Пример иллюстрирует порядок действий, но в реальном коде значения должны браться только после `$request->validate(...)`, а все обязательные поля — проверяться по правилам проекта.

### 11.4 Статусы

Задай допустимые статусы заранее, например:

```text
new → processing → completed
                 ↘ cancelled
```

Обычный пользователь не должен иметь возможность отправить `status=completed` в своей форме. Статус выставляет сервер или отдельное действие администратора с проверкой прав.

### 11.5 Профиль и история

Используй связь `User -> orders -> items`, подгружая связанные строки через `with('items')`. Это уменьшает число SQL-запросов и предотвращает проблему N+1.

## 12. Проверка данных и безопасность

Перед публикацией проверь каждую форму и маршрут.

## 13. Тестирование

### 13.1 Что проверять

Для каждого ключевого сценария составь тесты:

- гость видит публичный каталог;
- товар можно добавить в корзину;
- количество ограничено;
- гость не может открыть оформление, требующее входа;
- пользователь не оформляет заказ с пустой корзиной;
- заказ создаётся с актуальной ценой из БД;
- сумма и количество записаны верно;
- после успешного оформления корзина очищена;
- личный кабинет показывает только заказы вошедшего пользователя;
- невалидные данные не создают заказ.

### 13.2 Feature-тесты

```powershell
& W:\xampp\php\php.exe artisan make:test OrderTest
& W:\xampp\php\php.exe artisan test --filter=OrderTest
```

Для тестов используй отдельную тестовую базу или SQLite in-memory, если схема и используемые функции с ней совместимы. Не запускай `RefreshDatabase` на production-базе.

### 13.3 Миграции важны для тестов

Тест с `RefreshDatabase` запускает миграции на чистой базе. Если таблицы созданы вручную и нет миграций, тесты не смогут повторить рабочую схему. Это сигнал добавить корректный baseline схемы или подготовить изолированное тестовое окружение.

### 13.4 Проверка перед завершением функции

Минимум:

```powershell

& W:\xampp\php\php.exe artisan route:list
& W:\xampp\php\php.exe artisan migrate:status
& W:\xampp\php\php.exe artisan test
```

Дополнительно проверь Blade-компиляцию:

```powershell
& W:\xampp\php\php.exe artisan view:cache
& W:\xampp\php\php.exe artisan view:clear
```

Не заявляй, что тесты прошли, если запуск завершился ошибкой или тесты не запускались.

## 15. Частые ошибки

| Ошибка | Почему возникает | Как исправлять |
|---|---|---|
| `Class ... not found` | Namespace, имя файла/класса или Composer autoload не совпадают | Проверь `namespace`, PSR-4 и запусти `composer dump-autoload` |
| `Table not found` | Таблица не создана или имя отличается | Проверь `migrate:status`, `protected $table`, конфигурацию БД |
| `Unknown column` | Поле используется кодом, но отсутствует в схеме | Добавь безопасную миграцию и примени её |
| `Route [name] not defined` | Имя в `route()` не совпадает с `->name()` | Проверь `route:list` |
| `419 Page Expired` | Нет CSRF-токена или сессия истекла | Добавь `@csrf`, проверь сессии и домен |
| `MassAssignmentException` | Поле не разрешено в `$fillable` | Разрешай только ожидаемые поля; не расширяй бездумно |
| Заказ не сохраняется | Не создана БД/таблица, не проходит validation или FK | Посмотри ошибку и логи, не маскируй исключение |
| В списке неверная сумма | Цена или итоги берутся из браузера/не обновляются | Пересчитывай на сервере из БД |
| Пользователь видит чужую запись | Получение по глобальному ID без проверки владельца | Загружай через `$request->user()->relation()` или Policy |
| Тесты падают на чистой БД | Таблицы создавались вручную | Добавь migrations и настрой тестовую БД |
| Рабочий сайт сломался после обновления пакетов | Зависимости пересчитаны без проверки | Для воспроизведения используй `composer install`, обновляй поэтапно |
